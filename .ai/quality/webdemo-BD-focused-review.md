### D-1（P1）旧 Agent artifact 不可能是文档声明的 `52bf44a`，且 `SHA256SUMS` 自校验不能证明来源
- 位置：`tests/e2e/run_webdemo_upgrade.py:16-19`（"default 52bf44a, the commit the shipped build/ artifact records"）、`:59 OLD_COMMIT_DEFAULT`、`:60 SHIPPED_OLD`、`:248-262`；`tests/e2e/webdemo_upgrade_manifest.json:13`；commit message a4b568b。
- 实际反证：
  1. `build/linux-amd64/.proxypanel-build` 全文只有 `Generated by Build-Release.ps1`（30 字节），**不记录任何 commit**，所以“artifact records 52bf44a”这句话没有依据。
  2. `go version -m agent-old` → `dep golang.org/x/sys v0.36.0`；`git show 52bf44a:go.mod` → `x/sys v0.47.0`。全历史只有初始提交 `ec7ee10` 的 go.mod 是 `v0.36.0`（`git log -- go.mod` 逐一检查，之后 125 个提交都是 0.47.0）。故 artifact 来自 `ec7ee10` 时代（或带 0.36.0 的未跟踪树），**不是 52bf44a**。
  3. `:249-257` 的“验证”是拿 `build/linux-amd64/agent` 和**同目录**的 `SHA256SUMS` 比对；该 sum 文件与被测文件同属一个可写目录、无外部锚点/签名。实测所有条目（`.proxypanel-build`/`panel`/`configs/*`/`deploy/*`/`agent`）互相自洽，说明“未被改坏的副本”，**不能说明 commit 归属**。换掉 agent 同时换 SHA256SUMS 该检查依然通过。
- 影响：README/manifest/commit message 的“旧=52bf44a、SHA256SUMS 已验证”属于可复用声明，主合并后会变成不可复核的错误溯源；另一个隐患是若走 fallback `--old-commit 52bf44a` 重建，得到的二进制与 artifact 不同（依赖不同），两条路径严格来说不是同一“旧版本”，报告却并列描述。
- 最小修复：删掉“the commit the shipped build/ artifact records”；把 artifact 来源改写为“未知 commit 的官方打包产物（buildinfo 显示 x/sys v0.36.0 ⇒ 早于 52bf44a）”，或在 receipt 里落 `go version -m` 提炼的模块版本并断言“与 52bf44a 不等”；`SHA256SUMS` 校验说明改成“同目录完整性锚点，不构成 provenance”，并补一个仓库内固定的 known-good sha 常量。
- 建议补测：断言 `agent-old` 的 buildinfo 与 `--old-commit` 构建结果的 sha 不同，并显式记录二者关系（而不是隐含“字节可能不同”）。

### D-2（P1）core 26.3.23↔26.3.27 切换只有 Agent 自报版本串 + applied，没有真实 core 进程身份，也没有一次真实过流
- 位置：`tests/e2e/webdemo_upgrade_test.go:506-537`（switch / core rollback）、`:830-855 demoUpgradeWaitBudget/waitAgent`、`demoUpgradeRun.transfer` 只在 `:372` 被调用一次（旧 Agent + 旧 core 阶段）。
- 实际反证：
  - 判据是 `row.XrayVersion == wantCore`（`agents.xray_version`，来自 `internal/agent/supervisor/supervisor.go:1180-1214`，其值由 `checkCoreBinary` 执行 `xray version` 得到，`:442-456`）。switch/rollback 阶段只断言该串 + `applied==desired` + `outbox==0` + `export=403`，**没有任何一次经被切换 core 的代理请求**，也没有记录 core 的 `/proc/<pid>/exe`、starttime、pid。
  - 对比 Agent 二进制侧做得对（`:850` 用 `/proc/<pid>/exe == a.bin` 锁定真实进程），core 侧没有同等强度证明。
  - 附带的证据噪声：`transfer` 用 `r.env.newCore` 当客户端 core（`:879`），在“旧 core 阶段”就地引入了新 core 进程，命名上容易被读成“旧 core 已在服务”。
- 影响：用户点名的“不得仅改 config/path 或版本串冒升级”在 core 维度未被满足——只要 Agent 的 `xray version` 串和 apply 成功，就能出 PASS；真实 core 进程是否换了、是否还能服务无证据。（applied 前进通常需要 apply 成功，但测试没有断言这个因果，也没有失败诊断区分。）
- 最小修复：每阶段记录 `core` 子进程的 pid/exe/starttime 与 `xray version` 输出 sha，并对每个阶段做一次最小真实过流（当前 `transfer` 抽成可复用的 `probe()`），失败时报 core 日志；客户端 core 固定用与阶段无关的第三个二进制。
- 建议补测：core rollback 后 `core` pid 必须变化且 starttime 递增；同一 state 上 export=403 保持不变。

## B 域（原身份门禁 / 拒绝判据）

### B-1（P1）存在 `--skip-runtime-lock`，可在**未持锁**时产出 `status=pass`
- 位置：`tests/e2e/run_webdemo_dual.py:123-124`、`:164`、pass 判定 `:256-270`、receipt 写盘 `:332-337`。
- 实际反证：`if not args.skip_runtime_lock:` 之外没有任何约束；跳过时 receipt 既无 `runtime_lock_acquired` 也无 `runtime_lock_acquired=false`，状态机照常 `pass`（对比 E 被点名的旁路）。本次 final2 receipt 是 `runtime_lock_acquired=true / released=true`（真 flock `:166-176`），所以**这一次没问题**，但 runner 自身留了可复现的绿灯后门。manifest 里 runner 命令未带该 flag，但 flag 会随源合并进主。
- 影响：任何后续“只为了跑通”的人为调用都能拿到与正式 receipt 无法区分的 PASS，锁的串行化契约从证据上不可信。
- 最小修复：`--skip-runtime-lock` 直接让 `receipt['status']='not_run'`、`receipt['runtime_lock_acquired']=False`、`receipt['isolation_violation']=True`，或干脆从提交版删除该参数（authoring 用本地未提交补丁）。
- 建议补测：跑一次 `--skip-runtime-lock`，断言退出码非 0 且 receipt 非 pass。

### B-2（P1）拒绝判据是“任意 error”，超时/客户端 core 崩溃/本地 echo 故障都会被记成“凭据被拒”
- 位置：`webdemo_dual_test.go` `probeTCP`（`:986-1002`）、UDP `:1004-1085`；使用处 `:339-363`（expiry）、`:406-443`（撤销）、`:548-556`（恢复）、`:710`（崩溃后不复活）。
- 实际反证：所有负向断言形如 `if err := f.probeTCP(...); err == nil { t.Fatal(...) }`，`probeTCP` 把 `client.Get` 的任何错误（含 5s `http.Client.Timeout`、`connection reset`、client core 退出、SOCKS 握手失败）都返回为 error；`f.note` 里记录的 `refusal` 文本 `Get "http://127.0.0.1:38337": EOF` / `read: connection reset by peer` 恰好是“任何断连都算”。没有对“拒绝原因”的分类断言，也没有对被拒耗时的上界断言（只有外层 60s 循环）。
- 已具备的缓解（要如实记）：每次负向之前有同类正向控制（`:322-330`、`:534-539`、`:694`），撤销后还验证了新凭据可用（`:563`），所以“整条客户端链路已死”这种最坏误判大多会被邻近断言挡住；但“单次慢/抖动被计成拒绝”仍未被排除。
- 影响：用户点名的“不要把 anyerr/timeouts 当正确拒绝”。一段 timeouts/EOF 仍能凑出 PASS。
- 最小修复：`probeTCP` 返回分类错误（`socksDialErr / proxyStatusErr / bodyMismatch / tlsHandshake` 等），负向断言只接受“VLESS 用户被拒”这一类（例如 SOCKS 连接建立后首包即 EOF，或代理返 502 且远端 body 含拒绝原因），并要求 `elapsed < N`；同时断言发起请求时 client core 进程仍存活（pid+starttime）。
- 建议补测：注入“client core 被 SIGSTOP”场景，断言测试**失败**而不是记成“拒绝成功”。

### B-3（P1）“原既有业务进程身份保护”被收窄为 own-scope + TCP listener inode，UDP 与无监听的外来进程无保护也无反证
- 位置：`run_webdemo_dual.py:64-80 listeners()`（只扫 `tcp`,`tcp6`）、`:83-99 owned_cores`、`:180-198`（own scope 严格 / host inventory 仅信息）、`:312-326`（对比逻辑）。
- 实际反证：
  - `listeners()` 只读 `/proc/net/tcp{,6}`，`state=='0A'`，key=`proto:local:port`，value=inode → 只能证明“原本存在的 TCP 监听仍在同 inode”。**UDP 监听完全没有采集**，因此若 cleanup/测试碰到外来 UDP 服务（例如任何 dns/quic/echo）不会有任何痕迹。
  - `host_cores_before/after` 只做 XOR 差异（`:320-321`），本次 churn = `{1664602 消失, 1667458 新增}`（receipt 已列）。这与“别家 owned core 自然重启”一致，也与“B 误杀后别家重启”一致，**没有区分力**。而 `owned_scope_clean` 只要求 own scope 干净：`not owned_cores_before and not owned_cores_after and not timeout_recovered`（`:316-319`）——即“别人的任务自然退出”被完全忽略，正是复查要求里担心被“ownscope only”掩盖的形态。
  - 外来无监听进程（如 agent-lab 的 `proxypanel-agent -config /home/compile/Work/agent-lab/agent.json`，pid 625047，本次仍在）在 before 快照里被记了，但 after 从不校验，等于没有保护断言。
- 影响：“既有业务进程身份保护”的实证强度下降；误杀的检测依赖的只是“代码域没匹配到”，不是观测。
- 最小修复（最小改动即可显著加强）：`listeners()` 增加 `udp`,`udp6`（bound socket 无 `0A`，按本地地址+port 收）；cleanup 里把**每次 kill 的匹配理由**写进 receipt（`matched_root/reason`），并对 `host_before` 中“不是本次 root 匹配的 pid”做 after 存在性断言（允许 churn 但要分类：消失的 pid 必须在本次 `recovered/leftover` 名单里才允许）。
- 建议补测：制造“外来 core 在本次运行期间被别家停掉”，断言 receipt 里被标注为 foreign_churn 而非污染；再制造“外来 UDP 监听”，断言 after 仍在。

### B-4（P2，可作为可复用实证）真 SOCKS5 UDP、cleanup 精确性、证据无秘密这三项成立
- UDP：`probeUDP`（`:1006-1085`）是完整 SOCKS5 `UDP ASSOCIATE`（cmd `0x03`、atyp 分派、UDP 报文体 `00 00 00 01 + addr + payload`），返回负载与 `wdd-real-udp-node-N` 逐字节比对（`:322-330`）；`clientFor` 的 inbound 明确 `"udp": true`、routing `network: "tcp,udp"`（`:966-976`）。**是 UDP 而不是 TCP 里塞 UDP**。
