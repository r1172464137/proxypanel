# product-readiness 技术预研报告

**输入：** 本轮产品改造请求、范围选择、[PRD 草稿](../prd/core/product-readiness.md)、[候选故事](../user-stories/core/product-readiness.md)、[决策账本](../decision-log/product-readiness.md)。  
**调研基线：** `/home/compile/Work/proxypanel` 的 `3435f1d`；独立副本与前轮证据仅作为候选修复来源。  
**结论性质：** 实现可行性和交付前提，不是验收报告。

## 1. 需求理解

### 1.1 本轮目标

交付成熟私有面板：管理员能部署、开通和排障，成员能加入、导入客户端和查看服务状态。界面文案、信息架构与业务闭环一起改；不扩展交易业务。

### 1.2 技术能力需求

- 保留现有后端、前端和节点执行架构，提升默认体验，不另起一套产品。
- 多页面对同一授权、同步和用量状态使用一致语义。
- 原生节点配置无损编辑，密钥替换一致，TLS 材料与客户端兼容检查真实有效。
- 候选安全/存储/Agent/协议修复先形成单一可验证版本，不直接覆盖主分支或既有服务。
- 把真实集成与浏览器验收入口收敛为项目可复现能力，脱离当前工作区的硬编码路径和临时口令。
- 现有数据与节点本地状态的升级可核对；迁移风险不能由换文案掩盖。

### 1.3 本阶段明确选择

采用“保留现有栈、整合可信基础、重做任务路径、以统一候选版本验收”的单一路线。不重写为其他语言，不引入支付系统，不换一套 UI 框架。

## 3. 差距与事实证据

### 3.1 文案与流程差距

源码盘点发现：邀请页使用“服务端原子兑换”，成员页暴露内部拒绝文案，部分重置动作以“订阅链接”为按钮名；工作台和运行详情将大量篇幅用于声明“来自真实接口”，而非呈现当前影响和下一步。

这些问题不能靠全局字符串替换解决：必须区分邀请是否预分配服务、保存与同步、链接重置与连接撤权，以及账号状态与代理状态。界面改名不等于底层业务改名。

### 3.2 候选修复完整性

以下是本轮只读检查，不是重新运行后的通过判定。

| 候选来源 | 已核对事实 | 进入整合前的要求 |
|---|---|---|

| agent 独立副本 | 23 个改动文件；现有 patch 仅 20 个，缺 3 个测试文件；既有文件也可能含后续修改 | 从最终 WIP 重新导出完整候选并重跑受影响验证，旧 patch 不直接采用 |

| frontend/protocol 独立副本 | 经两轮 TLS 语义核查，有更新 patch、核心探针及前端日志 | 真实后端回读、换钥、跨 origin、网络不确定与完整浏览器整体验证 |

### 3.3 已知整合交叉

- security 与 store 共同修改 `internal/panel/api/admin2.go`、`internal/panel/store/members.go`、`internal/panel/store/ops.go`。
- 两个候选分别定义事务恢复门禁，不能同时保留同名实现；普通写冻结与自助改密例外须在合并后重新证明。
- 邀请/会话原子性与历史周期/迁移互相影响，不能把“能应用补丁”当业务兼容。
- TLS 归一化、客户端参数、前端高级编辑和 Agent 实际加载必须按真实链路一起验，不能只看各包单测。

### 3.4 原有数字不能直接复用

- Go 501 PASS 事件、前端 178 PASS 和旧浏览器 867/867，属于不同历史基线，不证明整合后的版本。
- 11 个遗留 Docker 用例被跳过；它们硬编码旧资源，不能直接启用并破坏已有栈。
- 初次完整客户端矩阵保存过失败，后续分片重测产生其他结果；这些是多个 run，不标为一次 54 格全通过。保留运行关联，在同候选版本复验。
- `rollback_applied` 和坏节点隔离有未收尾记录，属于必须复核的运行风险。
- govulncheck JSON 模式成功退出不代表无漏洞；可达、导入包和仅模块级告警分别报告。

## 4. 技术路线与依赖研究

### 4.1 收敛路线

| 需求 | 选定方向 | 集成与兼容约束 | 依据 |
|---|---|---|---|
| 产品体验 | 沿用 Vue、Router、Tailwind、Reka 及现有表格/反馈组件 | 按任务重组，不换框架，不生成无数据支撑的控制台 |
| 可信业务基础 | 在单独整合分支审查、合并并验证现有候选修复 | 未提交树需内容指纹，测试、产物和迁移必须对应同一树 |
| 节点与客户端 | 沿用官方 Xray 和已有投影层 | 固定版本矩阵；不支持要明确，禁止删参数伪造兼容 |
| 部署 | 面板单 Go 进程，宿主 nginx 终止 TLS | 两种前端归属都验，不反转用户部署决定 |
| 自动验收 | 复用项目 Go/数据库/Xray/Playwright 入口，补齐项目内可配置执行与证据适配 | 不复制秘密，不依赖个人目录，故障测试串行，资源归属检查后才清理 |
| 交付纪律 | 按 t-design → t-task/t-run 或 t-super-run → 独立 review/accept 推进 | 最多5个并发（Sol只读审阅、DeepSeek机械清点）；主助手做阶段收口，不能以子代理自述放行 |

### 4.2 库研究结论

**现有依赖栈可满足需求，无需引入新的应用库。新增 UI/后端框架数量为 0。**

依赖安全升级与新增库是不同工作：现有候选将 pgx、x/crypto、x/sys、x/text 等升级到修复版本。该升级要在整合树重新构建、运行数据库/核心回归并扫描；未调用的模块告警也单列说明，不能写成“绝对无漏洞”。

本阶段没有新增库选择或缺失的库 API 事实，因此不为凑流程调用 Context7；外部资料仅用于产品模式和表达原则，不用来证明本地兼容性。

### 4.3 产品模式研究

- Remnawave：从首次设置走到客户端实际导入，强调交付闭环；本项目不照搬其全部分组、计费或拓展能力。
- Tailscale：结构化默认操作与高级原生配置共存，有助于降低常用路径认知负担。
- Carbon：就地反馈、明确下一步、限制无关通知、只对真正关键风险中断操作；用于替换每页自证型长说明。

### 4.4 确定约束

- 不执行面向其他栈的新项目初始化，不迁到 Rust/React。
- 不直接在既有部署上跑破坏性恢复、暂停、数据库重建或核心故障注入。
- 不因为“环境给了”就读取并传播私钥、密码或完整订阅配置。
- 原始 SQL 迁移和 Agent 本地状态不能盲目覆盖；升级前的资料核对是上线门禁。
- 不把 Chrome 调试协议、Playwright CLI、模拟请求和截图占位混为同一种证据。

## 5. 影响分析

### 5.1 后端

- `internal/panel/api`：保存/恢复/权限/错误反馈及安全候选整合，保持调用者兼容。
- `internal/panel/store`、`access`、`period`、`usagecalc`：授权、快照、周期、账本、批次与迁移一致性。
- `internal/panel/protocol`、`clientconfig`、`xrayconf`：无损配置、TLS 与真实客户端投影。
- `internal/agent/state`、`supervisor`、`xray`、`reporting`：收紧授权、持久化、采样顺序、进程恢复及安全停机。
- `go.mod`、`go.sum`：安全依赖升级和可重复构建。

### 5.2 前端

- `web/src/components`：导航、表单、确认、影响预览、结果与三态反馈。
- `web/src/views/admin`、`web/src/views/me`、`web/src/views/auth`：按故事重组任务入口及主信息。
- `web/src/lib`、`web/src/api`、`web/src/router`：一致表达、配置保留、提交核对与兼容路由。

### 5.3 持久化影响

候选修复涉及周期历史、归属历史、幂等和异常资料保护，需要新增迁移及既有库升级验证。这里不冻结任何表结构或迁移实现。对历史无法证明的资料，先阻断升级/交付并要求核对，不自动接受候选补丁的暂停或补算行为。

### 5.4 部署与测试

- `deploy`、`.github/workflows/images.yml`：宿主反代、单进程镜像、两种托管、安装升级和发布门禁。
- `scripts`、`tests/e2e`、`web/tests`：消除旧环境硬编码、复用真实自动化入口、补足故障/权限/客户端/浏览器证据和清理核查。
- `docs`：按最终事实同步部署、用户上手、诊断与恢复说明；不在未验收时改成“生产已验证”。

### 5.5 风险与执行门禁

| 风险 | 等级 | 缓解和完成条件 |
|---|---|---|
| 补丁不对应最终 WIP 或日志早于改动 | P0 | 重新形成完整交付、内容指纹及必要重测，旧摘要不可直接验收 |
| 历史周期/权限或迁移策略无法证明 | P0 | 新库与旧库升级、失败回滚、历史守恒及异常资料核对；不破坏现有数据 |
| 事务恢复门禁与密码救援例外冲突 | P0 | 合并后单一定义、并发进入恢复和组合变更的真实回归 |
| 坏节点/慢校验拖延其他节点撤权 | P0 | 跨节点故障、既有连接与本地到期实测，不用单节点正常路径代替 |
| 更换 TLS/REALITY 或配置编辑造成不可连接 | P0 | 真实浏览器编辑、后端回读、核心加载与握手完整链路 |
| 列表截断或未知状态被当成全部/正常 | P1 | 真实分页/搜索、范围变化、空与错状态、状态来源核验 |
| 验收入口依赖个人路径或遗漏工具 | P1 | 项目化可配置入口；执行前预检，缺必需工具时停止对应阶段 |
| 前后端独立发布版本不一致 | P1 | 版本关联、两种托管刷新登录、资源缓存与缺失资源验证 |

## 6. 可行性判定

### 6.1 结论

**可行（有条件）。** 当前架构和依赖可承载目标产品；主要工作是可信整合和交互闭环，不是新栈研发。条件是先关闭基础一致性和升级风险，再进入同候选版本的端到端验收。此结论不表示候选补丁已经通过合并验收。

### 6.2 验证动作，不作为用户决策延期

| 对象 | 责任阶段 | 完成条件 | 失败影响 |
|---|---|---|---|
| WIP 与交付 patch/日志版本 | 可信基础整合 | 文件内容及构建产物可核对，重叠处有独立回归 | 阻断该候选采用 |
| 既有库、全新库和 Agent 状态升级 | 基础设计/测试 | 非破坏性迁移矩阵、历史资料和权限不被无声改写 | 阻断交付 |
| 真实客户端/浏览器/故障链路 | 最终验收 | 按故事与兼容矩阵记录真实结果，失败有修复复验 | 不标产品完成 |
| 执行工具 | 对应执行阶段前置预检 | Docker 使用获授权远端；Go 工具链与 Python 入口就绪；若技能调用 Chrome DevTools MCP，则先具备该工具 | 不跳过必要阶段，不伪造证据 |

当前 shell 无 Docker CLI，现有 Docker 经获授权 SSH 主机执行；Go 使用既有 SDK 环境入口。`uv` 当前不在 PATH；若按技能采用相应 Python 执行入口，先补齐并验证该 CLI。当前 MCP 仅发现 Context7，未发现 Chrome DevTools；不把既有 Playwright 日志冒充 MCP 渲染检查。这些是执行预检项，不改变已选产品范围。

### 6.3 显式假设

无影响产品范围或最终技术路线的未确认假设。外部用户效率收益未量化，不以虚构收益承诺推进。

## 7. 给后续阶段的输入

- PRD 与本报告保持同一范围，不因技术风险暗中裁掉私有面板主旅程。
- 进入设计时冻结状态语言、页面入口、候选补丁整合边界、升级保护和每个故事的验证责任，不在本报告提前设计端点或存储结构。

- 完成设计、任务和实现后再执行真实验收，不以本轮调研替代产品测试。
