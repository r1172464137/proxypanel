# 备份、恢复与控制代际协调

## 状态与原则

恢复门禁、generation 拒绝、同版本不同 generation 快照及旧授权不复活已有自动化测试；**隔离 Docker 环境中的真实备份→独立目标还原演练已完成（A14，实测见下）**。它不等于生产灾备：未配置 WAL 归档/PITR，没有连续可恢复水位，**不能宣称零数据损失或生产级 RPO/RTO**。

PostgreSQL 是业务/用量权威；Redis 清空不应影响会话鉴权或账本。Agent SQLite 存 token、最后快照、授权、计数器基线与未确认批次。不要只备份某一个 SQLite 主文件而遗漏 WAL，不要在运行时直接复制数据库文件当作一致备份。

## 备份集合

- PostgreSQL：匹配数据库主版本的 `pg_dump --format=custom`，专属数据库账号、受限输出文件；生产需根据所需 RPO 配置物理备份+WAL/PITR。
- master key：与数据库备份分离、加密托管，至少一份离线恢复副本；它不是可任意轮换的启动口令。
- Agent：维护窗口停止 Agent（确认核心被停），一致复制完整状态目录；或用受信 SQLite online backup API。记录 queue depth、已应用 generation/revision、备份时间、主机与核心版本。
- 配置/证书、发布包、SHA256SUMS、数据库迁移版本。订阅链接/token、私钥、代理凭据不得写入普通运行报告。
- 备份保留时限与日志/账本保留是不同概念。当前去重批次和原始账本不能随普通事件保留期删除。

## 恢复操作顺序

1. 阻断恢复后的面板与 Agent 通信，暂停普通写入。保存现状和故障证据，不覆写仍存活节点的 SQLite。若可能，先通过管理员恢复接口进入协调模式；不能假定旧备份已包含该状态。
2. 在**专用恢复目标**还原备份，先验证 master key 可解密、迁移版本匹配。不能覆盖他人的库或现有共享服务。不要在公开服务已接入时直接启动旧备份。迁移前缀完整、0 pending 的恢复库可执行正常 `Open`，但这只表示数据库内部 checksum/账本/周期/孤儿等启动核对通过，**不表示旧授权可信或可以接入 Agent**；升级停止态材料仅用于实际有待迁移文件的过渡，不是每次 schema-current 重启的永久前置。
3. 继续保持外部通信阻断，面板仅向本机管理员开放，登录后立即 `POST /api/v1/admin/recovery-mode/enter`（Cookie+CSRF）。在该事务完成、随机 generation 已轮换前，禁止暴露业务入口或连接任何 Agent；若无法保证网络隔离，不得启动恢复副本。该操作在一个事务中启用恢复门禁并更新面板与 Agent 登记的 generation，使用密码学随机正整数（不超过 JavaScript 安全整数上限），不依赖旧备份计数加一。**恢复后的 generation 必须与所有节点保存的旧 generation 不同**；随机化仅降低碰撞概率，不能替代逐节点核对。若发现碰撞，在隔离状态下重新进入恢复模式生成新值。未完成核对不得开放节点同步。
4. 核对备份后发生的停用、过期、撤权、密码/凭据轮换、订阅组变更。按审计及独立恢复记录恢复当前真实授权；无法证明的成员保持禁用。不能把“数据库能启动”当作“权限可信”。
5. 核对账本截止水位与各节点待上报队列。重复 batch_id/相同载荷可幂等重发；同 ID 异载荷必须停止并调查。Agent 已收到 ACK 并删除的历史批次，若未在恢复备份/WAL中，就无法从 Agent 队列再造。记录该缺口，不能把当前核心累计计数直接全量补进账本（会双计）。
6. 在管理员界面勾选 Agent 修订已核对、账本已核对；退出接口要求 `{ "confirm":"verified", "agent_revisions_checked":true, "ledger_checked":true }`。这些是操作人确认，不是自动审计证明。退出后面板推进修订，各 Agent 仍拒绝未显式接受的新 generation。
7. 每个节点停止 Agent，以同一服务账户运行：

   ```text
   agent -config /etc/proxypanel/agent.json -accept-generation <exact-generation>
   ```

   命令需获取本地状态独占锁。只有完成授权与账本核对后才能接受；不要通过清空状态目录绕过门禁。再启动 Agent，核对 generation/revision、实例回执、旧连接关闭及真实代理访问。部分节点失败应保持待协调/失败，不标整批成功。
8. 放开业务入口，验证订阅格式、成员权限、用量与告警。记录 RPO（最后可恢复账本与故障时间之差）、RTO（故障到验证完成）、不可恢复缺口及处置人。

## 隔离恢复演练实测（A14，2026-10-21，隔离 Docker）

本次演练只针对本项目自有测试数据，还原到**独立**目标（`ppaccept-20261021-restore`，回环 `25433`；恢复面板 `18444`），不覆盖源库、不动源容器。完整证据、断言与保留资源见 [docs/archive/verification/docker-recovery.md](../archive/verification/docker-recovery.md)。

| 指标 | 实测 |
| --- | --- |
| 备份账本 | 46,722,583 B / 214 batches |
| 可重放队列 | 70,093 B / 1 个离线批次 |
| ACK 已删、不可恢复 | 70,093 B / 1 batch（**不从存活源导入**伪造零缺口） |
| 计数器基线 | 124 baselines / 60 generations |
| RPO（ACK 采样窗口） | 7.467 s；备份年龄 75.52–76.19 s |
| 还原耗时 / 演练 RTO | 4.9013 s / 31.8674 s |
| 恢复后账本 | 46,792,676 B（重放后仍缺上述 70,093 B） |

- 恢复门禁、**新的随机 generation**、拒绝未显式接受的新代次、显式 `accept-generation`、队列精确一次、旧授权不复活、重启后保持、源栈状态未改，均由 `TestDockerRecovery` 断言并通过（`docker-recovery-2.log`，**PASS 120.64s**）。
- 只有 Agent1 的**停止态完整副本**参与协调；Agent2 原状态卷保留，且**未**被声称已协调。
- 本演练**没有**验证生产备份策略、WAL/PITR、跨机或更大数据量还原、全部节点同时故障；RTO 数值只是该次演练值，不是 SLA。

## 故障处置

| 故障 | 行为与操作 |
|---|---|
| PostgreSQL 不可用 | 不确认 usage；Agent 持久队列重试。不要清队列；面板 readiness 不通过 |
| Redis 不可用 | 登录限流退化为有界本地限制；PG 会话和账本仍权威；不允许 fail-open |
| 队列容量/本地存储失败 | Agent 停受影响核心以阻止继续产生无法可靠记录的流量；修复磁盘后核对再恢复 |
| 新控制 generation | Agent 保留最后可信授权，进入 coordination_required；已知到期仍本地收紧 |
| 无法证明遗留 PID 身份 | 拒绝杀进程/接管，不按名字误杀；操作人核对路径、创建身份和配置归属 |
| 技术配置无效 | 不替换可用配置；授权变化不能用带旧凭据的 last-good 配置回退 |
| 核心计数器重置 | 依核心 generation/基线处理，禁止负数和盲目累加；核对最终采样缺口 |

## 当前不能宣称完成的内容

- 生产环境的真实备份恢复演练及其 RPO/RTO 测量（**隔离 Docker 演练已完成**，见下文；不等同生产）。
- 连续 WAL 归档/异地加密备份的部署与恢复证明。
- 隔离演练中未量化未采样的核心尾数；不能用后续重放样本宣称“连续无缺口”。
- 所有节点同时重启、磁盘满、跨周期长时间离线与生产规模负载下的联合演练。
- 主库和全部节点状态同时永久丢失时的无损恢复；这是数据不可得，不应生成虚假账目。
