# 架构

一句话：**面板算，Agent 执行，Xray 跑流量。** 面板不碰节点机的 shell，Agent 不碰数据库。

```
                        ┌──────────────────────────────────────────┐
   浏览器 / 成员  ──TLS──▶│  面板 cmd/panel                          │
                        │  · HTTP API（/api/v1/**、/sub/{token}）  │
                        │  · 授权计算：谁能用哪个节点、还剩多少     │
                        │  · 订阅渲染：xray / sing-box / mihomo / v2rayN
                        │  · revision 推进 + 审计                   │
                        └───────┬───────────────────┬──────────────┘
                                │                   │
                        ┌───────▼──────┐    ┌───────▼──────┐
                        │ PostgreSQL   │    │ Redis        │
                        │ 全部业务数据  │    │ 仅登录限流    │
                        └──────────────┘    └──────────────┘
                                                ▲
                                                │ Agent 主动拉（短轮询）
                        ┌───────────────────────┴──────────────────┐
                        │  节点机：Agent cmd/agent                  │
                        │  · GET /agent/snapshot?revision=&generation=
                        │  · 逐节点生成 Xray 配置、校验、拉起进程    │
                        │  · POST /agent/applied（上报实例结果）     │
                        │  · POST /agent/usage（用量批次，幂等账本） │
                        └───────┬──────────────────────────────────┘
                                │ 每节点一个独立实例
                    ┌───────────▼───────────┐
                    │  xray (官方二进制)     │   ← 本项目不修改核心
                    │  20101 / 20102 / ...  │
                    └───────────────────────┘
```

## 为什么是 Agent 拉，而不是面板推

节点机通常在 NAT / 防火墙后面，面板不应该持有节点机的凭据或反向调用能力 ——
那样面板一旦被拿下，攻击者就能直接往每台节点机推配置。

所以方向反过来：Agent 拿着只属于自己那台服务器的 token 主动轮询。
面板只回答「你当前该是什么状态」，不需要能连到节点机。

代价是配置有延迟（默认 3–5 秒一次轮询），这是刻意的取舍 —— 撤权靠的是「下一次
快照立刻生效」，而不是「面板能即时执行命令」。

## revision 与 control_generation

两个独立的东西，别混：

| 概念 | 变的时候 | 作用 |
|---|---|---|
| `revision` (`desired_revision`) | 任何影响授权的改动（改成员、改节点、改组、改订阅） | Agent 靠它判断「要不要重新拉快照」 |
| `control_generation` | **只有进入恢复协调模式时** | 标识「授权来源代际」。变了说明状态可能来自另一份数据库 |

`revision` 涨了，Agent 拉新快照、应用、回报 `applied_revision`。两者相等即收敛。

`control_generation` 变了，Agent **不会**自动采纳：它会保留上一份已知授权并持续告警，
直到运维确认面板侧状态无误后显式执行：

```bash
bin/proxypanel-agent -config /etc/proxypanel/agent.json -accept-generation <精确值>
```

这条设计是为了挡住「从旧备份恢复后，已经被踢掉的人又被放回来」。代价是恢复模式
退出后必须人工确认一次，不能自动化。

## 授权计算的权威在哪

**只在面板。** 数据库里存的是「谁属于哪个组、组里有哪些节点、成员是否 active、
配额多少」；面板在每次渲染快照时算出「这台服务器上有哪些用户、各自什么凭据」。

Agent 拿到的是**结果**（`instances[].users[]`），不参与推导。这样：

- 改一条规则不用考虑各节点机的本地状态
- 节点机被入侵也拿不到别人的授权信息
- 排查时只需要看面板算出来的快照

## 硬撤权：立刻断，但有代价

停用成员 / 轮换凭据 / 关闭节点 → 下一次快照里不再有该用户 → Agent 发现实例的
用户集合变了 → **重启该节点的 Xray 实例**。

这是真的立刻断（已建立的连接也断），但代价是：**同一节点上的其他人也会断一下**。
所以设计上按「每节点一个实例」划分爆炸半径 —— 要让某个成员断，就接受同节点的人
被影响几秒；不接受就把成员拆到不同节点。

不存在「只热重载某个用户」的路径，因为 Xray 不支持从运行中的配置里精确摘掉一个用户。

## 用量计量：为什么漏报不会重复计

Agent 本地有 SQLite 队列，把用量切成批次上报。每批带：

- `batch_id`（Agent 生成，唯一）
- `agent_id`（服务端校验归属）
- `schema_version`、时间戳区间

面板侧入账本时按 `batch_id` 去重，重复提交同一批返回原来的结果，不会加两次。
所以网络抖动导致的重复上传是安全的 —— Agent 可以放心重试。

时间戳偏移过大 → `422 BATCH_CLOCK_SKEW`，避免把一批很旧的数据算进当前周期。

## 恢复协调模式解决什么

场景：你从三天前的数据库备份恢复。数据库里某个成员还是 active 的，但三天前你
把他踢了。直接让 Agent 拉快照 → 他就被放回来了。

恢复模式的流程：

1. `POST /admin/recovery-mode/enter` —— 冻结所有普通写入（含成员自助写），
   轮换 `control_generation`，Agent 拒绝自动采纳
2. 人工核对：成员状态、凭据、账本总额是否与预期一致
3. `POST /admin/recovery-mode/exit`，载荷 `{"confirm":"verified",
   "agent_revisions_checked":true,"ledger_checked":true}`
4. 对 Agent 执行一次 `-accept-generation`，让它重建实例

冻结期间只放行：登录、`/sub/{token}` 读取、改自己密码（自救），以及退出恢复模式本身
—— 否则会永久锁死。
